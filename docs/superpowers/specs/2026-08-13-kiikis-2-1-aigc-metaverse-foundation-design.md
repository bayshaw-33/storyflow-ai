# Kiikis 2.1：AIGC 元宇宙基础、KK 实时智能体与 IP 社区设计

**状态**：产品设计已批准，待用户复核书面规格并分阶段执行
**日期**：2026-08-13
**总体路线**：真实创作黄金路径牵引
**首批用户**：Kiikis 自有创作团队
**长期市场**：面向个人创作者的 To C 产品

## 1. 执行摘要

Kiikis 2.1 不把产品改造成另一个聚合大量模型的通用生成画布。它要把 Kiikis 已有的 Universe、Canon、Actor、Provenance 和资产授权方向，收敛成一条能由真实创作团队持续使用、并能对个人创作者开放的产品主线。

2.1 的主线是：

`结构化剧本 → 导演交接快照 → 动态宫格分镜 → 生产结果 → 持续世界资源 → 邀请/分享/使用/授权 → 社区发现与互动`

KK 不是这条主线末端的奖励，而是贯穿全站的 AI 交互层：

1. 首先是实时任务控制工具，持续显示任务状态、真实进度、失败、待确认和结果入口。
2. 其次是理解用户、Project 和 Universe 上下文的交互陪伴智能体。
3. 最后是账号级外观、皮肤、卡牌和收藏系统，并为未来抽卡经济建立可信的权益基础。

邀请、免费分享、使用和授权也不是发布后的最后环节。Universe、Project、Actor 或 Asset 创建时就具备所有权、可见性、协作者和授权状态。发布到社区只是增加公共发现能力，不创造所有权，也不改变已经存在的权利事实。

Kiikis 的长期方向是基于 AIGC 的元宇宙。2.1 不先造一个孤立的 3D 大厅，而是先建立持续存在且相互连接的创作者身份、KK、Universe、Actor、Project、作品、资产、版本、权利和衍生关系网络。未来可进入的 3D 世界、AI 角色生活和沉浸互动必须投射自同一套 Canon 和权利图谱。

## 2. 依据与判断原则

本设计综合了：

- 2026-08-13 本地竞品测评报告；
- Trae 六平台八维度报告；
- Kiikis 2.0 证据审计；
- 当前 `main` 分支和线上页面；
- 团队现行《契约之家》EP25–EP30 动态宫格分镜交付格式。

外部报告的共同判断是：Kiikis 的差异化在 IP 资产、Universe 连续性和 Provenance，短板在真实端到端闭环、Agent、协作、交互和市场验证。

报告中的页面、示例资产、授权记录和收益数字只能证明产品界面或数据契约存在，不能自动证明真实交易、真实结算或市场规模。2.1 的验收必须区分：

- 页面展示；
- 代码存在；
- 后端已连接；
- 真实用户旅程跑通；
- 真实支付或授权事实发生。

## 3. 产品定位

### 3.1 一句话定位

Kiikis 是由 KK 协助运行、以 Universe 和 Canon 为根、让创作者持续创建、连接、分享、使用和演化 AIGC 世界与 IP 资产的 To C 创作平台。

### 3.2 首发与长期用户

- 自有创作团队是 2.1 的第一个真实生产团队，用真实项目验证工作流、权限、失败处理、运营和社区种子内容。
- 对外产品仍以个人创作者为根。注册、默认设置、定价、文案和所有权都以个人账号为核心。
- 协作附着在具体资源上，不将产品改造成企业组织软件。

### 3.3 AIGC 元宇宙定义

2.1 中的“元宇宙”是持续世界网络，而不是 3D 场景同义词：

- 创作者拥有持续身份和 KK；
- Universe 拥有 Canon、时间线、世界规则和版本；
- Actor 可在不同 Universe 和 Project 中扮演不同角色，同时保持身份母版；
- Project、作品和资产记录来源、版本和生产过程；
- 邀请、分享、使用、改编和授权形成可审计的关系图；
- 社区让用户发现和进入这些世界及资源；
- 未来 3D 或沉浸式体验读取同一套世界和权利数据。

## 4. 目标与非目标

### 4.1 2.1 目标

1. 修复工作台严重压缩，以及 Dashboard/任务中心无法进入真实项目的 P0 基线问题。
2. 跑通一条无人工搬运的剧本到动态宫格分镜黄金路径。
3. 将 KK 上线为真实、跨页面、可恢复的实时任务与陪伴智能体。
4. 为 KK 上线账号级档案、外观、库存、装备和轻量社区展示。
5. 将 `/community` 从占位页升级为有治理能力的 IP 资产社区。
6. 让 Universe、Project、Actor 和 Asset 从创建时即可邀请、分享、使用或授权。
7. 支持内部团队所需的项目级轻协作。
8. 让 To C 会员订阅进入真实支付生命周期。
9. 以内测方式验证免费、邀请制和人工审核的资产使用及授权。
10. 建立可供未来抽卡、皮肤经济、自动结算和 3D 世界复用的稳定事实模型。

### 4.2 2.1 非目标

- 不做自由图文或视频灌水、生活内容、私信、群聊和通用群组。
- 不做企业组织层级、部门、席位采购、企业 SSO 或复杂算力预算。
- 不做公众自动分账、创作者自动提现或二级交易。
- 不上线付费概率抽卡、保底机制或宠物货币经济。
- 不追求接入最多 AI 模型；只接入黄金路径必需且可稳定运营的 Provider。
- 不建设与现有 Universe/Actor/权利模型分离的 3D 大厅或虚拟土地系统。

## 5. 总体架构

### 5.1 六个边界清晰的系统

1. **持续世界资源系统**：User、KK、Universe、Canon、Actor、Project、Episode、Scene、Shot、Work、Asset 和版本。
2. **黄金创作工作流**：剧本导演交接、动态宫格分镜、生产结果和生产包。
3. **KK 交互系统**：实时任务投影、对话智能体、权限确认、档案、成长、外观和库存。
4. **关系与权利系统**：协作者、分享、使用、改编、授权、来源归因和撤销。
5. **IP 社区系统**：对象发布、发现、关注、反应、收藏、评论、通知、举报、屏蔽和审核。
6. **订阅与权益系统**：Stripe 订阅、产品权益、人工交易事实和未来经济兼容的权益账本。

每个系统通过稳定 ID、版本和追加式创作事件协作。界面不得自行推断所有权、授权、任务完成或付费状态。

### 5.2 唯一事实源

- 结构化资源和不可变版本是创作事实源。
- 服务器写入的追加式事件是任务与业务变化的事实源。
- 服务器校验的 grants 是访问、协作、使用和改编权限事实源。
- Stripe webhook 是订阅付款与生命周期事实源。
- Entitlement ledger 是 KK 外观、订阅权益和未来经济资产的持有事实源。
- Community publication 是公共发现事实，不等于源资源或 IP 所有权。

## 6. 剧本到动态宫格分镜黄金路径

### 6.1 版本化导演交接

剧本工作台继续提供国际制作、Hollywood Spec 和亚洲制作等人类可读剧本格式，但下游分镜不再重新解析一段松散 Markdown。用户选择“定稿并进入分镜”时，系统生成不可变导演交接快照。

第一版 schema 固定为 `kiikis.screenplay-handoff/1`，至少包含：

- `projectId`、`universeId`、`episodeId`、`episodeNo`、`episodeTitle`；
- 稳定 `sceneId` 和显示编号，例如 `E25-S01`；
- `interiorExterior`、`locationId`、场景位置、时间；
- `continuityMode: NEW | CONTINUOUS`；
- 视觉主题、叙事功能、冲突、价值变化和转场接口；
- 角色引用、Actor/Character 母版版本、场景初始方位和人物动作；
- 剧本块、对白原文、对白译文、说话人和表演说明；
- 道具引用、文字道具不可读要求和关键物证；
- 场景母版、入口、空间方向、屏幕方向和 180 度轴线；
- 上一场承接和下一场落幅接口；
- 默认 `aspectRatio: 9:16`；
- Canon 快照版本、来源剧本版本和内容哈希；
- 创建者、创建时间和确认者。

导演交接必须由服务器生成稳定版本。修改剧本不会静默修改旧快照。

### 6.2 AI GC 动态宫格模板

团队提供的样本覆盖 EP25–EP30、49 场、365 个单格镜头。其字段顺序和导演规则成为 2.1 默认模板“AI GC 动态宫格”，但底层事实源为结构化数据。

第一版分镜 schema 固定为 `kiikis.dynamic-grid-storyboard/1`。

场级字段：

- 项目、集和稳定场景 ID；
- 场景位置、视觉主题和出场人物；
- `gridCount: 4 | 6 | 9 | 12`；
- `gridLayout: 2x2 | 2x3 | 3x3 | 3x4`；
- 格数判断理由；
- 整体生成要求；
- 场景母版和空间连续性；
- `continuityMode` 与首格策略；
- 统一摄影参数；
- 场级负面提示词；
- 来源交接版本、分析版本、修订号和内容哈希。

格级字段：

- 稳定 `shotId`、格序、镜头标题；
- 画面动作和叙事 beat；
- 人物方位、人物动作和屏幕方向；
- 景别、机位、焦段、角度、焦点与景深；
- 运镜起幅、路径、速度变化、视差、焦点变化和落幅；
- 台词原文、译文、情绪和后期说明；
- 道具、人物和场景资产版本引用；
- 与上一格的连续性及下一格/下一场转场接口；
- 图像提示词、视频提示词和负面提示词；
- `locked`、`userEdited`、`confirmed` 和来源哈希。

### 6.3 强制导演规则

- `NEW` 场景第 1 格必须是无人空镜，不得出现主要人物、群众演员或人物局部。
- `NEW` 首格必须包含明确运镜，不接受固定机位。
- `CONTINUOUS` 可承接上一镜动作、道具或视线，不强制空镜。
- 4/6/9/12 格由叙事和信息密度决定，不能机械固定为九宫格。
- 增加空镜后不得删除关键剧情，也不得为凑数重复动作。
- 每一格独立采用 9:16 构图。
- 相邻格必须改变景别、机位距离或观察关系。
- 必须保持人物身份、服装、道具、空间地理、光线、时间、屏幕方向和轴线连续。
- 多空间蒙太奇分别绑定场景母版，禁止人物虚假同框。
- 画面中的文件、手机、报告、合同和屏幕文字不可读；台词只进入后期字段。
- 最后一格必须定义落幅和下一场接口。

违反可确定性规则时必须阻断确认；主观导演规则产生 warning，由用户确认或锁定。

### 6.4 修改传播

剧本更新后按 `sceneId` 和来源哈希计算差异：

- 未受影响场景保持不变。
- 没有人工修改或锁定的场景可以选择重新分析。
- 人工修改的场景显示字段级冲突，不自动覆盖。
- 锁定镜头永不自动覆盖。
- 用户可选择只更新对白、重新拆当前场、保留分镜但更新来源说明，或取消。
- 重新分析前自动创建不可变快照。
- 并发保存继续使用 revision/CAS；冲突允许另存快照，不允许绕过 CAS 覆盖当前状态。

### 6.5 确定性导出

分镜工作台从结构化数据稳定生成：

- `动态宫格分镜提示词.md`：严格按团队字段顺序；
- `storyboard.json`：完整结构化事实；
- `shot-list.csv`：一格一行；
- 按已启用 Provider 生成的视频提示词文件；
- 人物、场景和道具母版引用；
- 分镜图、已完成视频和生产包；
- manifest、SHA-256、来源版本、导出者和导出时间。

Markdown 是确定性视图，不在每次交接时重新让模型自由改写。

## 7. KK：实时 AI 交互与宠物系统

### 7.1 单一 KK 运行时

现有 `KKProvider/KK3D`、`GravityProvider/GravitySystem` 和 V2 KK 消息面板必须收敛为一套 KK 领域模型和一个全局运行时。不能继续存在相互独立的三套状态。

全局 KK 在所有登录后页面持续存在；`/companions` 升级为 KK 中心，提供档案、成长、外观、库存、装备历史、任务历史和隐私设置。全局 KK 是日常入口，KK 中心是完整管理面。

### 7.2 第一层：实时任务控制

KK 必须显示服务器真实数据：

- 排队、运行、流式生成、等待用户确认、重试、完成、失败和取消；
- 当前阶段、已完成工作单位、总工作单位和最近更新时间；
- 阻塞原因、错误摘要、已完成范围、费用或额度处理状态；
- 待确认事项和跳转到准确上下文的操作；
- 完成结果和对应资源；
- 可取消、可重试、不可重试和需要人工处理的区别。

只有 Provider 或工作流提供可验证工作单位时显示百分比，例如 `33/49 scenes`。否则显示阶段进度，不伪造 `68%` 之类的数字。

实时链路使用 Supabase Realtime 订阅经 RLS 过滤的任务/事件投影；断线时展示最后同步时间并进入重连状态。重连后按事件序号补拉。轮询是降级路径，不是第二事实源。

生产和 staging 默认关闭 KK fixture。fixture 只允许测试和显式本地演示。

### 7.3 第二层：交互陪伴智能体

KK 的上下文由服务端组合：

- 用户偏好和语言；
- 当前页面、当前资源和当前操作；
- 当前 Project、Episode、Scene 或 Universe；
- 经授权可见的 Canon、Actor 和资产；
- 近期任务、失败、待确认和用户已采纳的决定；
- KK 档案、外观和成长状态。

KK 可以解释、提醒、导航、生成草稿、提出下一步和发起可撤销操作。以下动作必须显示明确确认界面并由用户执行：

- 定稿；
- 接受或修改 Canon；
- 发布或下架；
- 邀请、授权、撤销授权或转移所有权；
- 付费、退款或消费权益；
- 删除资源；
- 覆盖人工编辑或锁定结果。

### 7.4 第三层：外观、卡牌与库存

2.1 上线：

- 账号绑定的 KK profile；
- 版本化外观/卡牌目录；
- 稳定内容 ID、稀有度、版本、可用时间和展示资源；
- 追加式 entitlement ledger；
- 账户库存投影；
- 装备槽和装备历史；
- 创作成就解锁；
- 用户可控的社区展示隐私。

2.1 不上线概率付费抽取、保底、二级交易或影响创作能力的 pay-to-win。未来抽卡只能在此权益模型上增加 draw、pool、probability disclosure、pity 和支付记录，不能以客户端 localStorage 作为所有权。

### 7.5 成长原则

KK 成长只响应有业务意义且经过服务器确认的事件，例如完成第一部作品、确认一季剧本、完成生产包、首次分享、首次获得收藏、首次被合法使用或改编。重复生成、垃圾发布或频繁点击不得刷成长。

## 8. 资源出生即具备权利

### 8.1 资源所有权

每个 Universe、Project、Actor、Work 和可授权 Asset 创建时必须有：

- 唯一 owner；
- 默认私有 visibility；
- 可为空的协作者集合；
- 可为空的分享、使用和改编 grants；
- 来源及版本；
- Provenance 起点。

协作者参与创作不会自动获得 IP 所有权。所有权转移必须是独立、显式、可审计且需要二次确认的操作。

### 8.2 四类关系

1. **Collaboration grant**：允许在指定资源范围查看、评论、编辑、审阅或批准。
2. **Share grant**：允许被邀请用户或持有链接的访客查看指定版本和字段。
3. **Usage grant**：允许在指定 Project 或范围内使用 Actor/Asset。
4. **Adaptation grant**：允许从指定 Universe/Work 创建衍生 Project，并保留来源关系。

角色固定为 `viewer`、`commenter`、`editor`、`reviewer`。`owner` 不是 grant 角色；批准发布、授权或 Canon 的最终权限仍由 owner 或 owner 明确委托的 reviewer 执行。

grant 必须包含 resource type/id、grantee、scope、status、有效期、创建者、撤销信息和来源条件。默认最小范围，不从 Project 自动扩大到整个 Universe。

撤销阻止未来访问或新使用，但不删除已经发生且当时合规的使用、来源归因、版本或证据。

### 8.3 社区发布与权利分离

资源可以在未发布社区时被邀请协作、免费分享或授权。发布到社区只创建 publication 和发现索引。删除 publication 不删除源资源。暂停公开发现可以独立于协作者访问和现有有效授权。

## 9. 项目级轻协作

2.1 支持：

- 以账号、邮箱或邀请链接邀请；
- Universe、Project、Episode 或 Asset 范围；
- viewer/commenter/editor/reviewer；
- 任务分配和待办；
- 场景或对象评论；
- 请求审阅、批准、驳回和修改意见；
- 活动历史和 KK 通知；
- 移除成员和撤销未来访问。

2.1 不展示企业部门、员工目录、席位采购、组织级算力池或企业 SSO。即使底层复用已有 team 表，产品语义和所有权仍以个人创建者及资源 grant 为准。

## 10. IP 资产社区

### 10.1 一级内容对象

社区动态只能绑定：

- Published Work；
- Published Universe；
- Published Actor/Asset；
- 用户选择公开的生产日志或里程碑；
- 用户选择公开的 KK 成就和装备外观。

不提供与创作对象无关的自由发帖入口。

### 10.2 核心功能

- 发现页：关注、最新、精选和类型入口；
- 创作者主页：作品、Universe、Actor、徽章和可选 KK 展示；
- 关注创作者；
- like/reaction；
- 收藏到个人 collection；
- 对象评论与回复；
- 分享；
- 进入 Universe 或查看 Actor Passport；
- 根据权利状态发起邀请、免费使用、分享或改编申请；
- 通知中心；
- 举报、屏蔽和审核状态。

每个社区卡片必须显示 owner、对象类型、来源/Provenance 摘要、可见性和当前用户允许执行的动作。不能用“购买”“收益”文案包装 fixture 或未开放能力。

### 10.3 社区数据边界

publication 引用源资源及固定展示版本。对象更新后由 owner 决定 publication 跟随最新或保持 pinned，不静默替换社区已讨论内容。

关注、反应和收藏必须唯一且幂等。计数是服务器投影，可重算，不能作为不可变事实源。评论支持软删除并保留审核证据。屏蔽后双方内容和互动立即按产品规则隐藏。

### 10.4 审核与安全

社区开放时必须同时上线：

- 发布前基础检查；
- 评论和对象举报；
- 用户屏蔽；
- moderation queue；
- 管理员隐藏 publication、冻结评论、恢复和记录理由；
- 用户申诉；
- 不可篡改的审核活动记录。

审核可暂停公共发现，不应直接删除源 Project、Universe 或 Asset。涉及明显违法或账号安全事件时，另走账号/资源处置流程。

## 11. 追加式创作事件

### 11.1 事件用途

同一事件流驱动：

- KK 实时任务与对话提醒；
- 通知；
- 协作活动；
- 社区里程碑；
- KK 成长和成就；
- 审计和运营指标。

### 11.2 事件模型

在现有 task events 基础上新增通用、追加式 creative event，至少包含：

- `eventId` 和全局/用户可排序序号；
- `eventType` 和 schema version；
- actor user/system；
- owner/audience user IDs；
- resource type/id/version；
- 可选 task/job ID；
- 幂等键；
- 安全裁剪后的 payload；
- visibility；
- occurred/created 时间。

业务写入和事件写入必须位于同一数据库事务，采用 transactional outbox 语义。消费者按 event ID 幂等处理。事件 payload 不包含 Provider key、完整敏感 prompt、私有存储路径、支付密钥或不必要的个人信息。

2.1 使用 Postgres/Supabase，不引入新的外部消息代理。若未来规模要求，可从 outbox 扩展，但不能更改领域事件语义。

## 12. 订阅与交易内测

### 12.1 真实会员订阅

Stripe 是 2.1 的支付系统。现有 Checkout 继续作为发起入口，但成功 URL 只表示用户返回网站，不能授予权益。

必须补齐：

- Stripe customer 与 Kiikis user 映射；
- webhook 签名验证和原始 body 处理；
- webhook event ID 幂等；
- checkout 完成、subscription created/updated/deleted、invoice paid/payment failed 和 refund 状态同步；
- 订阅状态、period end、cancel at period end 和 plan price 映射；
- Customer Portal 或等价的取消/更新支付方式入口；
- webhook 重放和乱序防护；
- plan entitlement 由服务器读取同步后的订阅状态。

2.1 退款可由运营在 Stripe 执行，系统通过 webhook 同步。前端不得自行把查询参数当作付款成功。

### 12.2 社区交易内测

2.1 的资产与改编交易只开放：

- 免费 grant；
- 邀请制 grant；
- 人工批准的内测订单/授权；
- 人工结算意图和状态。

订单、grant、归因、费用、争议和结算状态都必须记录事实。未发生真实资金移动时，UI 明确显示“免费”“邀请制”“人工审核”或“人工结算”，不得显示自动收益或虚假余额。

公众付费资产、自动分账和提现不在 2.1 公测范围。

## 13. 错误与恢复

### 13.1 AI 或生产任务失败

KK 和任务中心显示失败阶段、可理解原因、已完成范围、额度处理和重试资格。系统保留输入、中间结果和幂等键。未交付的计费任务不得静默扣费；按当前计费规则自动退款或记录待处理状态。

### 13.2 实时连接中断

显示重连和最后同步时间，不继续动画伪装进度。恢复后从已确认事件序号补拉。重复事件不得重复发通知、KK 奖励、授权或社区动态。

### 13.3 上游内容变化

按场显示影响范围；人工编辑和锁定内容进入冲突解决，不自动覆盖。任何重分析先快照。

### 13.4 权限或授权冲突

服务器 fail closed，返回稳定错误码、缺失权限、可批准者和现有使用是否继续有效。客户端不能扩大 visibility、role 或 grant scope。

### 13.5 社区举报

举报立即确认，屏蔽立即生效。举报者身份不向被举报方公开。审核处置保留证据、理由、申诉和恢复路径。

### 13.6 支付异常

Checkout 创建失败不改变 plan。成功跳转但 webhook 未到达时显示“正在确认付款”。付款失败、取消或退款按 Stripe 同步状态降低或延续权益，不由客户端猜测。

## 14. 隐私、安全与审计

- 所有资源读写和社区投影均使用服务端权限校验与 RLS 双重保护。
- service role 只在服务器使用。
- KK 只获得当前用户经授权的上下文；社区公开信息与私有创作上下文分离。
- 分享 token、邀请 token 和 webhook secret 不写入日志或客户端 DTO。
- 对象删除、所有权转移、授权、撤销、发布、审核和支付状态写入审计记录。
- Provenance 记录事实和来源，不做法律所有权裁决。
- 数据导出和账号删除必须区分用户内容、合作历史、合规证据和法律保留需求。

## 15. 测试设计

### 15.1 契约与单元测试

- screenplay handoff schema 与版本兼容；
- 动态 4/6/9/12 格规则；
- NEW 首格无人且有运镜；
- CONTINUOUS 承接；
- Markdown 确定性快照；
- source hash、diff、lock 和 CAS 冲突；
- grant 范围、状态和撤销语义；
- creative event 幂等；
- KK 任务投影和成长防刷；
- inventory/entitlement ledger；
- community follow/reaction/save/comment 幂等；
- Stripe webhook 签名、重复、乱序和计划映射。

### 15.2 集成测试

- 剧本定稿生成 handoff 并进入分镜；
- 分镜分析、人工修改、锁定、上游更新和冲突解决；
- 导出团队 Markdown、JSON、CSV 和生产包；
- 任务事件通过 Realtime 到 KK，断线后补拉；
- 创建 Universe/Project/Actor 后立即邀请、分享或授予免费使用；
- 发布社区后互动、通知、举报、屏蔽、审核和恢复；
- Stripe Checkout → webhook → entitlement → 取消/退款。

### 15.3 权限与安全测试

为每个资源和 grant 类型建立 owner、协作者、普通登录用户和匿名用户矩阵。所有越权写入必须失败。必须覆盖客户端伪造 owner、扩大 scope、读取私有 KK 上下文、读取私有评论和重放 webhook。

### 15.4 真实 UAT

内部团队用真实项目完成至少一个与附件规模相当的六集批次，并满足：

- 不复制粘贴剧本到分镜；
- 4/6/9/12 格均能产生；
- 人工锁定和上游差异保护被真实使用；
- 导出的 Markdown 可直接进入团队现行生产流程；
- KK 真实显示任务、错误和待确认；
- 至少一次邀请协作、一次免费分享、一次免费使用 grant；
- 至少一个 Universe/Actor/Work 进入邀请社区并完成互动和举报演练。

## 16. 上线门槛

### Gate 0：产品基线

- Dashboard 和工作台在 390、768、1024、1440、1920、2560 视口不被全局侧栏遮挡或压缩；
- “继续创作”、Dashboard 任务卡和任务中心“查看详情”进入正确项目；
- 无点击无响应、内部 404、开放重定向或 fixture 冒充真实对象。

### Gate 1：内部团队黄金路径

- 一次真实六集批次端到端完成；
- 剧本到分镜无人工搬运；
- 团队确认 Markdown 和生产包可直接使用；
- 无未解决 P0/P1 数据丢失或覆盖问题。

### Gate 2：KK 真实实时

- staging/prod fixture 关闭；
- 所有可见任务来自服务器；
- 可验证任务使用真实单位，其他任务只显示阶段；
- 跨页面和刷新恢复；
- 正常网络下事件到可见 UI 的 p95 不超过 3 秒；
- 重连后 10 秒内完成缺失事件补拉。

### Gate 3：资源权利

- Universe、Project 和 Actor 创建后均能邀请、分享或授权；
- grant/RLS 自动化矩阵全部通过；
- 撤销不抹除历史事实；
- 所有权转移和授权有确认及审计。

### Gate 4：社区安全运营

- 发现、主页、关注、反应、收藏、评论和通知跑通；
- 举报、屏蔽、审核、申诉和恢复跑通；
- 管理员可以只暂停公共发现而不破坏源资产；
- 无未解决 P0/P1 安全、隐私或审核缺陷。

### Gate 5：订阅与观测

- Stripe 测试环境完整生命周期通过；
- 用内部真实小额订阅完成付款、取消和退款验证；
- 权益只由 webhook 同步状态授予；
- 可观测任务成功率、失败类型、事件延迟、剧本到分镜完成率、社区发布/互动/授权漏斗、订阅状态和 Provider 成本。

只有 Gate 0–5 共六个门禁全部通过，才能移除 `/community` 的 Coming Soon 并宣布 Kiikis 2.1 对外全面上线。

## 17. 推进顺序与工作包

本设计是统一产品规格，但实现必须拆成可独立验收的工作包：

1. **Phase 0 / P0 基线修复**：工作台布局、Dashboard/任务中心真实项目跳转。
2. **Phase 1 / 数据事件地基**：迁移、Creative Event、RLS、feature flags、fixture 与观测门禁。
3. **Phase 2 / 剧本到动态宫格分镜**：handoff、4/6/9/12 格、锁定、diff、确定性导出。
4. **Phase 3 / KK**：Realtime、单一 runtime、陪伴权限、profile、库存、装备和成就。
5. **Phase 4 / 权利与协作**：ownership、collaboration/share/use/adaptation/license grants、邀请和审阅。
6. **Phase 5 / IP 社区**：publication、发现、互动、通知、举报、屏蔽、审核和申诉。
7. **Phase 6 / 订阅与交易内测**：Stripe lifecycle、entitlements、免费/邀请/人工授权。
8. **Phase 7 / UAT 与发布**：真实六集生产、邀请社区、运行手册和 Gate 0–5 验收。

依赖顺序：Phase 0 → 1；Phase 1 → 2、3、4；Phase 3+4 → 5；Phase 1+4 → 6；Phase 7 等待 Phase 2–6 全部通过。可并行开发，但不得绕过依赖验收。

## 18. 迁移与兼容策略

- 不修改已经进入历史的迁移；2.1 创建新的 forward-only migrations。
- 现有 deferred 社区迁移只作为设计参考，不通过删除注释或改写历史文件上线。
- 现有公开 profile、Universe share、Actor marketplace 和 V2 licensing 优先迁移/适配，不并行维护两套产品事实。
- 旧 `/companions` redirect 在 KK 中心上线时替换；旧链接保持兼容。
- `/community` 在 Gate 通过前继续 feature flag 限制，不能提前公开一个缺少审核的 feed。
- fixture 模式必须显式、可观测且不能在 staging/prod 默认启用。
- 社区计数、KK 状态和权益从事实表生成投影，投影可以重建。

## 19. 成功指标

2.1 公测后的核心指标围绕真实闭环，而不是页面访问：

- Screenplay handoff 创建率；
- handoff 到已确认分镜的完成率和耗时；
- 上游修改导致的冲突率及无数据丢失解决率；
- KK 任务查看、结果跳转、确认和恢复成功率；
- 首次创建后邀请/分享/use grant 发生率；
- 有效 publication 的浏览、收藏、评论、进入 Universe 和申请使用转化；
- 创作者次周继续创作率；
- 订阅 Checkout 到 webhook-confirmed active 的转化；
- AI 任务成功率、事件延迟和单位成功产出的 Provider 成本。

指标不预设虚构增长目标。内部团队基线和邀请 beta 数据形成首轮实际目标。

## 20. 最终产品边界

Kiikis 2.1 的完整定义不是“新增宠物页和社区页”，而是：

- 真实剧本与动态宫格生产可以连续工作；
- KK 成为全站实时 AI 入口和持续陪伴；
- 所有创作资源出生即具备所有权、协作、分享和授权能力；
- 社区可以发现和互动这些真实资源，同时可安全运营；
- 订阅真实，交易能力诚实地处于邀请/人工内测；
- 所有数据和关系可以成为未来 AIGC 元宇宙、3D 世界、AI 角色生活和宠物经济的同一事实基础。
