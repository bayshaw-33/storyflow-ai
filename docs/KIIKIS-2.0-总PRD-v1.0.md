## 0. 执行摘要

KIIKIS 1.0 已经完成小说、剧本、美术、分镜、视频、演员等工作台的基本框架，部分功能已可实际使用。当前主要矛盾不再是“有没有功能”，而是：

1. 各工作台仍像彼此相邻的工具，尚未形成顺畅的整体生产系统；
2. Universe 作为 KIIKIS 的最大卖点之一，目前仍处于初级开发阶段；
3. Atlas Cloud 已提供多模型基础，但模型能力、选择逻辑、质量、成本和任务状态没有被清楚地呈现给用户；
4. 创作成果、版本、来源、Canon 和衍生关系尚未稳定沉淀为可复用资产；
5. 演员和 IP 资产已经具备生态雏形，但授权、调用、订单和价值回流尚未形成闭环。

KIIKIS 2.0 不是重做所有工作台，而是同时完成三条产品线：

- A 线：Universe、平台内核与资产基础；
- B 线：创作体验与生产闭环；
- C 线：演员与 IP 资产生态。

三条线并行建设，但不平均用力。Universe 产品化与短剧生产样板闭环是 P0；生态线从可使用、可授权、可留痕的最小闭环开始，并在 2.0 周期内形成真实产品。

KIIKIS 2.0 的核心产品原则是：

> 体验上 Project-first，资产上 Universe-first。

用户可以直接从一个想法、一份剧本或一个制作任务开始，不必先填写复杂的 Universe。系统在创作过程中自动建立或绑定 Universe，并把经用户确认的角色、场景、世界规则、Canon、镜头和成片资产逐步回流，让 Universe 随作品自然生长。

## 1. 产品定义

### 1.1 一句话定位

KIIKIS 是以 Universe 为长期资产母体、以 AI 工作台为生产界面、以演员与 IP 资产网络为价值延伸的 AI 原生创作与影视生产系统。

### 1.2 Kiikis 2.0 的版本主题

> 从“工作台框架已经存在”，升级为“作品能够顺畅完成、Universe 能够持续生长、资产能够被继承和流通”。

### 1.3 2.0 必须回答的三个问题

1. 用户能否不理解复杂架构，也能顺畅完成一部作品？
2. 每次创作能否真正增强 Universe，而不是生成一批彼此失联的文件？
3. 沉淀的演员与 IP 资产能否在权利清楚的前提下被再次调用并产生价值？

### 1.4 2.0 不是什么

- 不是重新开发一套与 1.0 平行的工作台；
- 不是把所有模型堆到同一个选择器中；
- 不是让用户先填写完整世界观数据库；
- 不是未经确认就让 AI 自动改写 Canon；
- 不是在权利和履约能力不足时贸然开放无限制交易市场；
- 不是以增加页面和功能数量作为成功标准。

## 2. 当前产品基线

### 2.1 已有基础

- 小说、剧本、歌曲、美术、分镜、视频与制作工作台已经有基本框架；
- 部分工作台能够完成独立任务；
- Atlas Cloud 已接入图像、视频和语言模型能力，部分页面已支持模型选择；
- 视频和美术任务已有排队、运行、完成、失败等状态基础；
- Universe 已有概览、资产、作品、Canon、Inbox、关系图、分享和部分 AI 提取能力；
- 演员库已具备 Actor、Character、Portrayal 的部分结构和平台共享基础；
- 项目已有权限、额度、证据、导出和后台管理基础。

### 2.2 当前核心问题

#### 工作台可用但割裂

- 用户进入产品后不清楚下一步；
- 同一项目在不同工作台之间切换时，上下文、资产和完成状态不够连续；
- 生成、比较、修改、确认、回流和导出没有统一操作语义；
- 用户经常面对“生成中”而不知道实际发生了什么。

#### Universe 有框架但没有真正成为产品核心

- Universe 主要依赖用户主动进入详情页管理；
- 项目绑定、继承和成果回流没有贯穿所有工作台；
- 本地存储和云端数据仍有双轨迹象；
- Canon Check、Inbox 和资产关系存在功能零件，但没有形成自然闭环；
- 用户尚未明显感受到“第二次创作比第一次更快、更一致”。

#### 多模型能力存在但不够显性

- 用户不知道为什么当前任务推荐某个模型；
- 不清楚模型的质量、速度、成本和适用任务差异；
- 模型选择集中在部分工作台，跨工作台体验不统一；
- 缺少任务级路由记录、成本反馈和可解释降级。

#### 资产生态尚未闭环

- 资产公开、私有、团队和可授权状态不够统一；
- 使用条件、调用记录、衍生关系和证据没有形成完整产品；
- 交易前后的权限、撤销、订单和收益记录仍需建设。

## 3. 产品哲学

### 3.1 创意熵减

KIIKIS 不只生成内容，还要防止创作信息在工具切换、多人协作和长期生产中消散。

产品要求：

- 已确认设定不会被静默覆盖；
- AI 修改必须展示影响范围；
- 角色、场景、道具和世界规则有稳定身份；
- 用户随时知道当前版本、来源和下一步；
- 失败、降级和未同步必须显式可见。

### 3.2 技因演化

每个创意资产都应当能够被继承、组合、修改和追溯。

产品要求：

- 资产不仅有文件版本，还要有父版本、来源作品和衍生用途；
- 项目从 Universe 继承的是明确快照，而不是模糊复制；
- 项目成果以候选变更回流 Universe；
- 用户能查看某个角色、设定或资产如何演变。

### 3.3 知本主义

创作者的设定、资产、选择和贡献应当被记录，并在未来具备明确的授权和价值回流机制。

产品要求：

- 创建者、贡献者、使用者和衍生者关系清楚；
- 使用不等于所有；
- 共享和授权有明确范围、期限和商业条件；
- 平台能够保存调用、订单、授权和证据记录；
- 证据辅助核验，不宣称自动产生法律权利。

### 3.4 长期主义

- 模型可以替换，Universe 和资产关系必须留下；
- 快速生成不能以破坏角色一致性和来源关系为代价；
- 先完成真实生产闭环，再扩大生态规模；
- 任何市场能力都以权利、履约和治理为前提。

## 4. 目标用户与核心任务

### 4.1 AI GC 导演 / 制片人

核心任务：

- 从剧本快速建立角色、场景、分镜和镜头生产计划；
- 在多个模型之间选择合适能力；
- 保持长剧集、跨集和跨季一致性；
- 看到任务进度、异常和成本；
- 输出可进入专业剪辑流程的素材包。

### 4.2 编剧 / IP 主理人

核心任务：

- 建立和维护世界规则、人物关系、时间线与秘密；
- 把小说、剧本、短剧和衍生内容放在同一 Universe 中；
- 检查新内容与既有 Canon 的冲突；
- 了解修改一个设定会影响哪些作品。

### 4.3 美术与视觉团队

核心任务：

- 继承已确认角色、场景和道具；
- 比较多模型结果并局部修改；
- 锁定主版本；
- 让后续分镜和视频始终使用已确认资产。

### 4.4 演员 / 资产创建者

核心任务：

- 建立稳定的 AI 演员身份或创意资产档案；
- 设定可见性和使用条件；
- 查看被哪些作品调用；
- 获得授权、订单和收益记录。

### 4.5 团队管理员

核心任务：

- 管理成员、权限、额度和模型连接；
- 查看失败任务、资源消耗和生产状态；
- 管理资产授权、争议和证据；
- 保证团队交付可追踪。

## 5. 产品信息架构

### 5.1 一级结构

1. 首页 / Dashboard
2. 项目 / Projects
3. Universe
4. 创作工作台
5. 制作工作台
6. 演员与资产
7. 资产市场
8. 任务中心
9. 团队与后台

### 5.2 首页

首页不是功能菜单，应回答：

- 我正在做什么；
- 哪些任务完成了；
- 哪个项目需要我确认；
- 下一步最值得做什么；
- 最近哪些 Universe 和资产发生了变化。

首页固定区域：

- 继续创作；
- 等待确认；
- 运行中任务；
- 最近 Universe；
- 最近作品；
- 快速开始；
- KK 入口。

### 5.3 项目

项目是用户的短期生产容器。每个项目必须显示：

- 作品类型；
- 所属或待绑定 Universe；
- 当前生产阶段；
- 已确认资产；
- 运行中任务；
- 阻塞和下一步；
- 最近自动保存时间。

### 5.4 Universe

Universe 是长期 IP 母体，负责：

- 世界规则和 Canon；
- 角色、地点、组织、道具和概念；
- 关系与时间线；
- 作品和衍生关系；
- 继承快照；
- 候选回流；
- 版本和影响分析；
- 团队共享、授权和证据。

### 5.5 工作台

各工作台继续保留专业能力，但共享同一工作台外壳：

- 项目与 Universe 上下文；
- 当前阶段与下一步；
- 输入资产；
- 生成与模型设置；
- 结果比较；
- 修改和确认；
- 版本记录；
- 任务状态；
- 回流与导出。

### 5.6 演员与资产市场

分为两个入口：

- 我的资产：创建、管理、版本、权利和使用记录；
- 市场：发现、筛选、授权、调用和订单。

## 6. 核心用户旅程

### 6.1 首条样板：短剧完整闭环

1. 用户上传剧本或输入故事想法；
2. 系统创建项目，并建议新建或绑定 Universe；
3. AI 分析剧本，生成结构化角色、场景、道具、关系和 Canon 候选；
4. 用户确认关键候选，系统形成项目继承快照；
5. 用户进入角色与场景美术生产；
6. 系统推荐模型，用户可接受推荐或手动选择；
7. 用户比较结果、局部修改并锁定主版本；
8. 已确认资产自动进入分镜工作台；
9. 分镜转为镜头任务，批量生成关键帧和视频；
10. 任务中心和 KK 持续汇报排队、生成、入库、完成和失败；
11. 用户逐镜确认、替换或重做；
12. 系统导出剧本、镜头表、图片、视频、字幕、提示词和制作证据；
13. 已确认的角色、场景、Canon 和作品资产进入 Universe Inbox；
14. 用户接受、编辑后接受或拒绝；
15. Universe 生成新快照，下一集或下一季可以直接继承。

### 6.2 小说与剧本

- 允许从空白想法、已有大纲或完整文本开始；
- 对话式完成需求收集、结构规划和正文生成；
- 每阶段用户确认后进入下一阶段；
- 重新规划不得删除已有正文；
- 重要角色状态、关系、事件和世界规则作为 Universe 候选；
- 继续创作时继承指定 Universe 快照。

### 6.3 歌曲与衍生内容

- 歌曲可绑定 Universe、作品、角色或情节节点；
- 继承语言、时代、人物情绪和作品风格；
- 歌词与创作说明形成可回流候选；
- 2.0 不要求歌曲工作台重建，只要求完成统一绑定、状态、版本和回流契约。

## 7. A 线：Universe、平台内核与资产基础

### 7.1 Universe 创建与绑定

#### 需求

- 用户可以手动创建 Universe；
- 创建项目时系统建议新建、绑定或暂不绑定；
- 未绑定项目可以随时绑定；
- 一个项目只能有一个主 Universe，但可以记录外部引用；
- 创建项目时自动保存 Universe 继承快照；
- 绑定和解绑必须保留历史记录，不删除已产生资产。

#### 验收

- 新用户无需进入 Universe 页面即可开始项目；
- 完成首次结构分析后，系统能产生 Universe 候选；
- 同一项目重复提交不会生成重复 Universe 或重复主绑定；
- 刷新、换设备后绑定关系保持一致。

### 7.2 Universe Bible 与资产对象

Universe 必须支持：

- 核心命题和世界摘要；
- 世界规则；
- 角色；
- 地点；
- 组织；
- 道具；
- 概念；
- 关系；
- 时间线；
- Canon Fact；
- 秘密与未解线索；
- 作品列表；
- 资产与版本；
- 成员和权限。

每个对象必须包含：

- 稳定 ID；
- 名称和摘要；
- 状态：Draft、Canon、Alternative、Deprecated；
- 来源；
- 当前主版本；
- 被哪些作品使用；
- 最近更新时间；
- 可见性和权利信息。

### 7.3 继承快照

- 每个项目在创建、重大阶段确认和正式导出时生成 Universe 快照；
- 快照记录继承了哪些角色、规则、关系、时间线和资产版本；
- Universe 后续变化不会静默改写正在生产的项目；
- 用户可以选择“继续使用原快照”或“审阅并升级到新快照”；
- 升级前显示字段级差异和潜在影响。

### 7.4 候选回流 Inbox

- 工作台确认的结果自动生成 Universe Change Proposal；
- Proposal 必须包含来源项目、来源步骤、原文或资产、置信度、字段差异和建议动作；
- 用户可接受、编辑后接受、拒绝或暂缓；
- AI 不得绕过 Inbox 直接改写已锁定 Canon；
- 批量接受前显示影响摘要；
- 重复提取必须幂等。

### 7.5 Canon Check

- 在大纲确认、剧本定稿、分镜定稿和导出前可运行；
- 检查角色身份、关系、时间线、世界规则、地点、秘密和生产规则；
- 输出 Critical、Warning、Note；
- 每条问题必须引用目标内容和相关 Canon；
- 提供修复建议，但不自动修改；
- AI 不可用时明确失败，不显示虚假高分。

### 7.6 影响分析

当用户修改 Canon、角色身份、关系、时间线或主资产时：

- 显示受影响作品；
- 显示受影响项目快照；
- 显示受影响角色、场景、分镜和资产；
- 提供“仅更新 Universe”“创建新版本”“向指定项目提出升级建议”；
- 禁止直接跨项目覆盖。

### 7.7 资产谱系

每个正式资产版本必须记录：

- 父版本；
- 来源资产；
- 来源项目和步骤；
- 使用模型与生成任务；
- 人工选择；
- 修改说明；
- 被哪些项目和作品使用；
- 授权来源；
- 完整性校验信息。

用户看到的是可读的“演变记录”，不是数据库字段或技术日志。

### 7.8 Universe 健康度

健康度不使用单一虚假总分。显示六个可解释维度：

- Canon 完整性；
- 角色完整度；
- 关系和时间线完整度；
- 资产覆盖；
- 待处理候选；
- 冲突与过期快照。

每个维度提供具体待办入口。

### 7.9 团队与分享

- Owner、Editor、Contributor、Viewer 四级权限；
- 可按对象和作品控制可见范围；
- 分享链接可设置密码、期限和可见内容；
- 外部访问不暴露内部 ID、Prompt、存储路径和供应商信息；
- 权限变化不删除历史贡献和合法使用记录。

## 8. B 线：创作体验与生产闭环

### 8.1 渐进式开始

创建入口只先询问完成当前任务必需的信息：

- 想做什么；
- 从什么开始；
- 目标内容类型；
- 是否已有剧本或素材；
- 是否关联已有 Universe。

复杂市场、集数、语言、模型和生产参数在需要时再询问。

### 8.2 统一工作台外壳

所有核心工作台采用同一交互结构：

- 顶部：项目、Universe、保存状态、阶段和任务；
- 左侧：步骤、资产和版本；
- 中间：当前创作区；
- 右侧：AI 对话、建议、模型和上下文；
- 底部或浮层：运行任务和异常。

移动端优先支持查看、确认、任务管理和轻量修改，不强行承载完整专业生产。

### 8.3 对话驱动

- AI 主动询问缺失信息；
- 一次只处理一个关键决策；
- 用户确认后进入下一阶段；
- AI 修改先提供预览或差异；
- 对话与结构化字段双向同步；
- 用户可随时切换为手动编辑；
- 不允许重新规划静默删除已有正文或已确认资产。

### 8.4 多模型产品化

#### 默认模式：智能选择

系统根据任务、参考图、目标质量、速度和账户额度推荐模型，并说明：

- 为什么推荐；
- 预计速度区间；
- 成本等级；
- 适合的任务；
- 主要限制。

#### 专业模式：手动选择

用户可查看和筛选可用模型：

- 文本、图像、编辑、视频、声音；
- 质量；
- 速度；
- 成本；
- 参考图能力；
- 一致性能力；
- 当前可用状态。

#### 路由记录

每个任务保存：

- 用户选择或系统推荐；
- 实际调用模型；
- 是否发生降级；
- 降级原因；
- 估算与实际成本；
- 结果状态。

### 8.5 结果比较、修改和确认

- 每次生成至少支持候选比较；
- 用户可以锁定主版本；
- 支持局部重做，不强迫整批重生成；
- 修改保留父版本；
- 失败不清空已成功结果；
- 确认动作明确标记“用于本项目”“提交 Universe 候选”“设为资产主版本”；
- 任何跨范围动作必须显式确认。

### 8.6 全局任务中心

统一聚合文本、图像、视频、声音、转存、导出和分析任务。

每个任务展示：

- 任务名称；
- 所属项目和工作台；
- 当前阶段；
- 已完成数量和总数；
- 已耗时；
- 预计时间区间及置信度；
- 当前结果；
- 失败原因；
- 可执行动作；
- 完成后的入口。

不提供真实进度的模型不得伪造精确百分比，应显示阶段、耗时、历史区间和下一事件。

### 8.7 KK 全局助手

KK 是产品的全局交互与任务反馈层，不是独立主线。

职责：

- 汇报任务进度；
- 提醒需要用户确认的事项；
- 解释当前页面和下一步；
- 帮用户跳转到结果、错误或待处理项；
- 在用户授权后记住播报偏好和工作习惯；
- 保留互动和陪伴感。

播报频率由用户选择：

- 频繁播报；
- 关键节点播报，默认推荐；
- 仅询问时播报。

KK 不承担：

- 擅自修改 Canon；
- 擅自确认生成结果；
- 隐藏真实失败；
- 以拟人表达代替可读任务信息。

### 8.8 短剧制作闭环

2.0 必须把以下链路作为首条生产样板跑通：

剧本 → 结构分析 → 角色/场景/道具 → 美术母版 → 分镜 → 关键帧 → 视频镜头 → 审核替换 → 导出 → Universe 回流。

必须满足：

- 每一步继承前一步已确认内容；
- 支持从任何中断点继续；
- 支持单镜重做和批量任务；
- 所有正式素材持久化；
- 导出包不依赖临时 URL；
- 完成后自动生成 Universe 候选，不要求用户重复录入。

### 8.9 导出与交付

标准短剧生产包至少包括：

- 剧本；
- 场景和镜头表；
- 角色、场景和道具参考；
- 分镜图；
- 视频镜头；
- 字幕或台词时间信息；
- 生成与人工确认记录；
- 缺失或失败清单；
- 制作证据包。

缺失关键内容时必须输出 partial failure，不得生成伪完整包。

## 9. C 线：演员与 IP 资产生态

### 9.1 生态范围

2.0 首期支持：

- 平台内免费使用；
- 非商业使用；
- 单项目商业使用；

- 团队内部使用；

- 授权资产和版本；
- 授权人和使用者；
- 使用项目；
- 使用范围；
- 地域和期限；
- 商业条件；
- 状态；
- 证据和撤销规则。

### 9.4 市场发现

- 搜索名称、标签、类型和适用方向；

- 不展示内部 Prompt、存储路径和敏感元数据；
- 推荐必须可解释，不以付费排序伪装自然结果。

### 9.5 调用资产

用户获得授权后：

- 可选择目标项目和角色/用途；
- 系统创建使用记录；
- 创建项目级副本或 Portrayal，不修改原资产；
- 保留原创建者和来源关系；
- 资产撤销后停止新调用，但保留已有合法作品和历史记录。

### 9.6 订单与收益

2.0 建立最小商业闭环：

- 价格和授权条件；
- 下单；
- 支付状态；
- Usage Grant；
- 退款和取消状态；
- 创建者收入账本；
- 平台服务费记录；
- 管理员人工结算入口。

自动化跨境分账、税务和复杂版税瀑布不作为 2.0 上线前阻塞项，进入后续阶段；2.0 不得将人工结算描述为自动分账。

### 9.7 治理

- 举报侵权、冒用肖像、虚假来源和不当内容；
- 管理员可暂停新授权；
- 下架不删除历史交易和证据；
- 争议资产明确标记；
- 平台规则和变更日志可查询。

## 10. 核心领域契约

### 10.1 主要对象

| 对象 | 作用 |
|---|---|
| Universe | 长期 IP 母体 |
| Work / Project | 一次具体创作或生产 |
| Universe Entity | 角色、地点、组织、道具、规则和概念 |
| Canon Fact | 已确认且可锁定的事实 |
| Relationship | 实体之间的关系及历史 |
| Timeline Event | 世界或作品时间线事件 |
| Inheritance Snapshot | 项目创建或阶段确认时继承的 Universe 版本 |
| Change Proposal | 项目向 Universe 提交的候选变更 |
| Asset | 可复用资产身份 |
| Asset Version | 资产的具体版本 |
| Generation Job | AI 任务及其生命周期 |
| Model Decision | 模型推荐、选择、降级和成本记录 |
| Actor | 可跨作品复用的演员身份 |
| Character | Universe 中的故事角色 |
| Portrayal | Actor 在某作品中扮演 Character 的具体演绎 |
| License Offer | 资产发布者定义的授权条件 |
| Usage Grant | 一次明确的使用授权 |
| Evidence Event | 创作、选择、发布、授权和导出的关键事实 |

### 10.2 强制关系

- Actor 不等于 Character；
- Character 不等于 Portrayal；
- Project 必须至多有一个主 Universe；
- Project 继承 Universe 时必须产生快照；
- Work 变体不能直接覆盖 Universe Canon；
- Asset Version 必须属于一个 Asset；
- 正式使用必须指向稳定 Asset Version，不指向临时 URL；
- Usage Grant 必须指向明确版本或明确的版本升级规则；
- 生成结果完成不等于用户确认；
- Evidence Event 记录事实，不做法律裁定。

### 10.3 状态

#### Change Proposal

Draft → Pending Review → Accepted / Edited and Accepted / Rejected / Deferred

#### Generation Job

Draft → Pending Confirm → Queued → Running → Result Ingesting → Completed / Partial Failure / Failed / Cancelled

#### Asset

Draft → Ready → Published → Suspended / Archived

#### Usage Grant

Pending → Active → Expired / Revoked for New Use / Cancelled / Disputed

## 11. 数据与技术边界

### 11.1 权威数据

- 云端数据库和持久化对象存储是正式资产的权威来源；
- localStorage 只允许保存草稿缓存、未同步提示和恢复线索；
- 本地草稿不得伪装为已同步；
- 正式导出不得依赖 Provider 临时 URL；
- 任何迁移必须是可重入、可追踪且优先采用新增字段或新表。

### 11.2 API 版本

KIIKIS 2.0 新增接口统一使用 v2 命名空间和版本化契约。已有 1.0 接口通过适配器继续服务，避免一次性重写。

冻结契约版本：

- contract_version：2.0.0-alpha.1；
- breaking change 必须升级 contract_version；
- 同一开发波次内禁止静默改变字段含义；
- UI 可通过固定 fixture 和 Mock Server 独立开发；
- 后端可通过契约测试验证，不依赖 UI 完成。

### 11.3 功能开关

至少包含：

- universe_v2；
- workbench_shell_v2；
- task_center_v2；
- model_router_v2；
- marketplace_v2；
- licensing_v2；
- kk_companion_v2。

每条线可独立上线预览，不以其他线完成作为部署条件。

### 11.4 安全

- 服务端校验用户、团队、资产和项目归属；
- 客户端不得直接扩大资产可见性或授权范围；
- Provider 密钥、Prompt、存储路径和内部 ID 不进入公共 DTO；
- 真人肖像、第三方素材和公开发布需要明确权利声明；
- 订单、授权和证据记录禁止客户端任意修改。

- 每次外部调用形成 Usage Grant；

- 下架不破坏已有合法使用记录。

### 14.3 不等待规则

1. 同一波次中的任务不得依赖同波次另一个工具尚未完成的代码；
2. TRAE 使用冻结契约 fixture 开发，不等待 Codex API；

4. 所有新能力放在独立目录和功能开关后；
5. 数据迁移只做增量，不要求 UI 同时上线；
6. 页面先使用 Mock 可预览，API 就绪后通过客户端适配器切换；
7. 慢任务不阻止快任务提交和推送；
8. 一个工具不得承担“先开发、再等另一工具审查、再回来修改”的循环。

### 14.4 分支与推送

- 每个任务使用独立 worktree 和独立分支；
- Codex 分支：codex/K2-C-任务号-短名；
- TRAE 分支：trae/K2-T-任务号-短名；
- 每个任务只解决一个明确目标；
- 完成后执行该任务指定的最小检查；
- 检查通过后立即 commit 并 push 到远端分支；
- 不等待另一工具复核；
- Coze 收到 branch、commit、预览地址和检查摘要后，进入一次性最终验证；
- 未通过最终验证时创建新的修复任务，不把原任务拉回无尽往返。

“直接推送”指直接推送独立远端任务分支，不允许两个工具同时直接覆盖 main。

### 14.5 单次验证原则

#### 执行者

- 只运行任务相关测试；
- 涉及共享类型时额外运行一次 TypeScript 检查；
- 不为文案或局部 UI 修改运行全库完整回归；
- 通过后直接推送；
- 不验证另一工具的任务。

#### Coze

- 每个发布候选只运行一次集成门禁；
- 门禁包含契约、类型、关键路径和预览检查；
- 不安排 Codex 复查 TRAE、再由 TRAE复查 Codex；
- 失败项拆成新的定点修复任务；
- 非阻塞问题进入后续 Backlog，不拖住已完成任务。

## 16. Coze 派发模板

每张任务卡必须直接包含：

- Task ID；
- 一句话目标；
- 固定 base commit；
- contract_version；
- 唯一负责人；
- 允许修改的目录；
- 禁止修改的共享文件；
- 输入 fixture 或 API 契约；
- 明确输出；
- 3–5 条验收标准；
- 唯一最小验证命令；
- 分支名；
- commit 格式；
- push 后需要回报的 branch、commit、预览地址和检查摘要。

禁止出现：

- “顺便优化”；
- “视情况重构”；
- “等待另一工具完成”；
- “由另一工具复查后再修改”；
- 没有文件边界的全局任务；
- 一个任务同时横跨数据库、API、页面、视觉和发布。

## 17. 风险与缓解

### 17.1 Universe 再次停留在框架

风险：继续增加页面和字段，却没有真实继承与回流。  
缓解：所有 Universe 任务以“项目绑定 → 快照 → 回流 → 下一项目继承”为唯一 P0 验收链。

### 17.2 三条线同时建设造成范围失控

风险：功能数量增加但没有完成闭环。  
缓解：每条线只建设一个完整纵向切片；生态先做标准授权和人工结算，不提前建设复杂金融系统。

### 17.3 不同工具速度不一致

风险：快任务等待慢任务或反复交接。  
缓解：冻结契约、fixture、独立目录、功能开关、独立分支、单独集成任务。

### 17.4 直接推送破坏主分支

风险：并发覆盖和不可恢复冲突。  
缓解：直接推送独立远端分支；Coze 一次验证后合并；禁止多人直写 main。

### 17.5 为了减少验证而引入生产故障

风险：完全取消检查导致返工更大。  
缓解：执行者只做一次最小相关检查，Coze 每个候选只做一次集成门禁；取消重复跨工具验证，不取消基本正确性检查。

### 17.6 AI 自动破坏 Canon

风险：错误抽取污染长期 IP。  
缓解：所有 AI 更新进入 Change Proposal；锁定 Canon 必须人工确认；影响分析先于跨项目更新。

### 17.7 市场权利风险

风险：真人肖像、第三方素材和授权范围不清。  
缓解：权利状态、用途、期限、地域、撤销和证据成为发布与调用的强制条件。

## 18. Kiikis 2.0 总体验验收

2.0 只有同时满足以下条件才算完成：

1. 用户可以从剧本开始，不必先配置完整 Universe；
2. 项目能够建立或绑定 Universe，并保存继承快照；
3. 角色、场景、美术、分镜和视频能够继承已确认资产；
4. 用户可以随时看到任务处于什么阶段、为什么等待、完成后去哪里；
5. Atlas Cloud 多模型能力被清晰呈现，并支持智能和专业两种模式；
6. 短剧能够导出真实可用的制作包；
7. 完成作品后自动形成 Universe 候选，经用户确认后回流；
8. 下一集能够继承上一集确认后的 Universe；
9. 修改 Canon 能看到影响范围，不会静默覆盖项目；
10. 资产拥有版本、来源、衍生和使用关系；
11. 演员或资产可以发布标准授权，并被另一个项目合法调用；
12. 订单、授权和收益账本形成最小一致闭环；
13. Codex 与 TRAE 可以按本 PRD 独立执行，不因速度差互相等待；
14. 每个任务完成后直接推送独立分支，不进入反复交叉验证；
15. Coze 能以一次性最终验证决定合并或创建定点修复任务。

## 19. 最终产品判断

KIIKIS 2.0 的成功，不是页面更多，也不是模型更多，而是产生三个可被用户感知的结果：

> 用户第一次能更顺畅地完成作品；  
> 用户第二次能明显继承第一次的创作资产；  
> 用户长期能够让这些资产被安全复用、授权并产生价值。

这三个结果分别对应创作闭环、Universe 和资产生态。任何一条缺失，KIIKIS 都仍然只是功能集合；三条同时成立，KIIKIS 才真正成为 Universe-First 的 AI 原生 IP 生产系统。
